# 범용 코드작성 시방서

- **버전**: v1.3 FINAL
- **확정일**: 2026-09-26
- **적용 범위**: 언어·프레임워크·운영체제와 무관한 모든 소프트웨어 개발
- **목적**: 코드의 안전성, 정확성, 최소 필요 복잡도, 변경 안정성, 가독성, 테스트 가능성, 성능, 유지보수성을 공통 기준으로 통제한다.
- **적용 방식**: 플랫폼·제품 전용 시방서는 본 문서를 상속하며, 동일 원칙을 반복하기보다 환경별 추가 규칙과 예외만 정의한다.
- **문서 성격**: 코드 작성·수정의 공통 하위표준. 제품별 UI·배포·업데이트·보안·릴리즈 계약을 대체하지 않는다.
- **교차검증 기준**: Google Engineering Practices, OWASP Secure Coding/Code Review, NIST SSDF, SLSA, PyPA의 일반 개발·보안·재현성 원칙과 Ponytail v4.10.0의 reuse-first·YAGNI·root-cause·minimum-working-diff 철학을 참고하되 특정 조직·언어·AI 호스트에 종속된 절차는 강제하지 않는다.

---

## 0. 규범어와 우선 원칙

### 0.1 규범어

- **필수**: 특별한 상위 계약 또는 명시적 예외가 없으면 반드시 지킨다.
- **권장**: 합리적 사유가 없으면 따른다.
- **허용**: 조건을 충족하면 사용할 수 있다.
- **금지**: 상위 계약의 명시적 예외가 없는 한 사용하지 않는다.

### 0.2 판단 우선순위

```text
안전·데이터 무결성
→ 사용자 요구·기능 정확성
→ 공개계약·호환성
→ 단순성·가독성·유지보수성
→ 성능
→ 미세 최적화
```

1. KISS와 YAGNI를 기본값으로 둔다.
2. 설계 원칙 적용 자체가 과설계·파일 증가·추상화 증가의 원인이 되어서는 안 된다.
3. 변경은 요청 목적과 직접 영향범위로 제한하고 관련 없는 정상 동작을 함께 바꾸지 않는다.
4. 암묵적 동작보다 명시적 계약과 상태를 우선한다.
5. 성능은 데이터 규모와 알고리즘 복잡도를 먼저 고려하고, 복잡한 최적화는 측정 근거를 가진다.
6. 검증은 변경 위험에 비례한다. 코드 변경의 기본은 targeted regression이며, 전체 회귀·패키징·실기 검증은 상위 제품/릴리즈 시방서가 요구할 때 추가한다.
7. 언어·프로젝트에 이미 합의된 style guide, formatter, linter, type/static analyzer가 있으면 개인 취향보다 이를 우선한다.
8. 외부 의존성·도구체인·런타임 가정은 암묵적으로 두지 않고 필요한 범위에서 선언·고정·검증한다.

### 0.3 구현 전 최소복잡도 결정 사다리

새 구현을 추가하기 전 다음 순서로 판단한다. **실제 실행 경로와 요구사항을 이해한 뒤** 첫 번째로 충분한 선택지에서 멈춘다.

```text
정말 필요한가?
→ 기존 코드에 이미 있는가?
→ 표준 라이브러리로 가능한가?
→ 플랫폼·프레임워크 네이티브 기능으로 가능한가?
→ 이미 설치된 의존성으로 가능한가?
→ 작고 직접적인 구현으로 가능한가?
→ 그래도 필요할 때만 최소 신규 구현
```

1. 이 사다리는 분석을 생략하기 위한 규칙이 아니라, 분석 후 불필요한 구현을 제거하기 위한 규칙이다.
2. 여러 선택지가 같은 요구를 충족하면 더 위 단계의 해법을 우선한다.
3. 줄 수가 가장 적은 코드가 아니라 **전체 시스템의 개념 수·변경면적·의존성·운영 부담이 가장 작은 해법**을 선택한다.
4. 가장 작은 diff가 잘못된 계층을 수정한다면 최소 변경으로 보지 않는다. 올바른 owner·공통 원인·계약 경계를 수정하는 것이 우선이다.
5. 보안, 데이터 무결성, 접근성, 신뢰경계 검증, 손실 방지 오류처리, 명시된 호환성 요구는 단순화를 이유로 제거하지 않는다.

# Part 1. 설계·구조

## 1. KISS — Keep It Simple

가장 단순하게 **정확한** 구조를 선택한다. 짧은 코드가 아니라 의도와 흐름을 쉽게 이해할 수 있는 코드가 기준이다.

## 2. DRY — Don't Repeat Yourself

동일한 업무규칙·검증·계산·상태판정을 여러 곳에 복사하지 않는다. 단, 단순히 코드 모양이 비슷하다는 이유만으로 성급한 공통 추상화를 만들지 않는다.

## 3. YAGNI — You Aren't Gonna Need It

확정되지 않은 미래 요구를 위해 인터페이스, 팩토리, 플러그인 계층, 캐시, 병렬구조, 확장 포인트를 미리 만들지 않는다.

특히 다음은 실제 두 번째 사용·구현·변경 이유가 확인되기 전 기본적으로 만들지 않는다.

- 구현체 하나뿐인 interface/abstract base
- 제품 하나뿐인 factory
- 전략 하나뿐인 strategy
- 호출을 그대로 전달하는 wrapper
- 실질적인 경계 가치가 없는 service/repository 계층
- 한 번만 쓰이는 범용 utility
- 사용자가 바꾸지 않는 config/feature flag
- 플러그인 하나뿐인 plugin system
- 현재 소비자가 없는 compatibility layer

추상화는 실제 중복 제거, 실제 경계 보호, 실제 다중 구현 또는 독립적 변경 이유가 있을 때 추가한다.

## 4. SRP — 단일 책임 원칙

함수·클래스·모듈은 하나의 명확한 책임과 변경 이유를 갖도록 한다. 서로 다른 이유로 변경되는 기능은 분리한다.

## 5. OCP — 개방-폐쇄 원칙

반복 확장이 실제 발생하는 지점은 등록·전략·구성으로 확장 가능하게 설계한다. 확장 가능성이 확인되지 않은 곳에는 미리 추상화 계층을 만들지 않는다.

## 6. LSP — 리스코프 치환 원칙

하위 타입은 상위 타입의 입력·출력·예외·상태 계약을 깨지 않아야 한다. 계약을 지키기 어려운 상속은 독립 구현 또는 합성으로 바꾼다.

## 7. ISP — 인터페이스 분리 원칙

사용하지 않는 기능까지 강요하는 거대한 인터페이스보다 역할별 작은 계약을 사용한다.

## 8. 관심사의 분리

입력·표시, 업무규칙, 데이터 접근, 외부연동, 저장, 검증, 배포환경 의존성을 가능한 한 분리한다.

## 9. 합성 우선

상속은 실제 `is-a` 관계와 안정된 계약이 있을 때 사용한다. 기능 조합이 목적이면 합성을 우선한다.

## 10. 디미터 법칙·경계 존중

다른 객체의 내부 구조를 깊게 탐색하거나 우회 접근하지 않는다. 필요한 동작은 명확한 API·서비스·어댑터 경계를 통해 요청한다.

## 11. 단일 기준원(Single Source of Truth)

동일한 상태·분류·업무규칙을 여러 구현이 따로 판단하지 않는다. 하나의 authoritative source가 계산·판정하고 UI·보고서·저장·검증이 그 결과를 사용한다.

---

## 11A. 단일 기준원과 변경 격리의 동시 적용

Single Source of Truth는 **동일 의미의 규칙·상태판정·계약을 중복 계산하지 않는다**는 원칙이지 모든 설정·스타일·상태·기능을 하나의 전역 객체나 공통 파일에 집중한다는 뜻이 아니다.

- 업무규칙의 진실은 하나일 수 있지만 UI 표현·저장·캐시·workflow 상태는 소비자별로 독립 소유할 수 있다.
- 공통화는 의미와 변경 이유가 같은 부분에만 적용한다.
- 서로 다른 기능의 우연히 같은 값은 동일 규칙으로 간주하지 않는다.
- local 문제를 해결하기 위해 shared source를 바꾸면 다른 소비자까지 변하므로, 먼저 local adaptation 경계를 확인한다.

## 11B. 변경 소유권과 전파범위

모듈·컴포넌트·설정·상태는 가능한 한 명확한 owner와 변경 이유를 가진다. 기본 변경범위는 local이며, shared 변경은 선언된 여러 소비자에게 같은 변경을 적용하려는 경우에만 수행한다.

1. shared로 승격하기 전 실제 복수 소비자, 동일 의미, 동일 계약, 동일 변경 이유를 확인한다.
2. 전역 mutable state, catch-all config, broad event bus, mega stylesheet, god service는 변경 전파범위를 불필요하게 넓히므로 피한다.
3. shared 변경 전 직접/간접 소비자를 확인하고 필요한 범위의 regression을 수행한다.
4. local 변경이 unrelated 동작을 바꾸면 정상 연쇄효과로 가정하지 말고 숨은 공유 상태·상속·selector·config 충돌을 조사한다.
5. 의도된 전역 정책 변경은 허용하되 변경 목적·migration·소비자 검증을 함께 수행한다.

## 11C. 의존성 방향과 순환 의존 최소화

1. 모듈·패키지 의존성은 가능한 한 한 방향으로 흐르게 하고 순환 의존을 피한다.
2. 상위 업무규칙이 하위 UI·저장·네트워크 구현 세부에 직접 끌려가지 않도록 인터페이스·어댑터·의존성 역전 등 필요한 최소 경계를 둔다.
3. import/init 시점의 숨은 I/O, 전역 등록, thread 시작, 파일수정 같은 부작용을 최소화한다. 초기화 부작용은 테스트·재사용·종료 순서를 어렵게 만든다.
4. 순환 의존을 해소하기 위해 무조건 새 계층을 추가하지 않고 책임 재배치·데이터 계약 단순화부터 검토한다.

## 11D. 최소 작업면적(Minimum Working Surface)

1. 변경 파일 수, 새 symbol 수, 새 public API 수, 새 dependency 수를 필요 이상으로 늘리지 않는다.
2. 같은 문제를 여러 호출부에서 각각 보정하기보다 공통 원인을 올바른 shared point에서 한 번 수정할 수 있는지 먼저 확인한다.
3. 단, 모든 것을 공통화하기 위해 unrelated 동작을 한 계층으로 합치지 않는다. **공통 원인과 공통 의미가 있을 때만 공통 수정**한다.
4. 삭제·재사용·치환으로 해결 가능한 경우 신규 구현보다 우선한다.
5. 이미 충분히 단순한 영역은 줄이기 자체를 목표로 다시 쓰지 않는다.
6. diff가 작다는 이유만으로 불완전한 검증, 취약한 알고리즘, 임시 예외처리, 손실 가능한 fallback을 선택하지 않는다.

# Part 2. 코드 계약·상태·오류

## 12. 가독성 우선

의도가 드러나는 이름, 짧고 명확한 함수, 단순한 분기, 일관된 데이터 모델을 사용한다. 영리하지만 해석이 어려운 코드보다 명백한 코드를 선택한다.

## 13. 명확한 입력·출력·부작용 계약

공개 함수·클래스·모듈은 호출자가 다음을 예측할 수 있어야 한다.

- 입력 타입과 허용 범위
- 반환값과 실패 방식
- 상태 변경 여부
- 파일·DB·네트워크·프로세스 등 주요 부작용
- 데이터·자원의 소유권과 정리 책임
- 취소 가능 여부와 취소 후 상태
- 단위·좌표계·시간대·로케일·문자 인코딩·정밀도처럼 값의 의미를 바꾸는 조건
- `null/None`, 빈 문자열, 빈 컬렉션, 0, 미설정처럼 서로 다른 의미를 갖는 값의 구분
- 순서가 계약에 포함되는지, 아니면 순서 비보장인지 여부

## 14. 상태전이는 명시적으로 관리

다단계 작업·비동기 작업·UI workflow처럼 상태가 중요한 코드는 상태를 암묵적 boolean 조합으로 흩어놓지 않는다. 가능한 한 유효한 상태와 전이를 명시하고, 중복 완료·중복 취소·중복 callback을 방지한다.

## 15. 명시적 오류처리

`except: pass`, 오류 무시, 실패를 정상값으로 위장하는 패턴을 금지한다. 오류는 필요한 문맥과 원인 체인을 보존해 상위 계층에 전달한다.

## 16. Fail Fast

필수 전제조건이 충족되지 않으면 가능한 한 초기에 명확히 실패한다. 잘못된 상태나 부분 저장을 만든 뒤 다른 위치에서 뒤늦게 실패하게 하지 않는다.

## 17. 외부 입력을 신뢰하지 않는다

사용자 입력, 파일, DB, API, 환경변수, 네트워크 응답, 외부 프로세스 결과는 필요한 범위에서 존재성·형식·범위·무결성·권한을 검증한다.

## 18. 안전한 기본값과 최소 권한

위험하거나 파괴적인 동작은 기본값으로 활성화하지 않는다. 필요 이상의 파일쓰기·네트워크·관리자권한·외부실행 권한을 요구하지 않는다.

## 18A. 주입 공격과 출력 경계 보호

외부 입력을 SQL, shell/command, HTML/JavaScript, URL/query, 파일경로, 템플릿 등에 문자열 결합으로 직접 삽입하지 않는다.

1. 가능한 경우 parameterized API, structured builder, 안전한 escaping/encoding API를 사용한다.
2. allowlist가 실용적인 경계에서는 허용값·허용형식을 우선 정의하고, 단순 blocklist만으로 안전성을 가정하지 않는다.
3. 출력 encoding은 사용되는 문맥에 맞게 적용한다. 하나의 escape 규칙을 모든 문맥에 재사용하지 않는다.
4. 파일경로·아카이브·업로드는 canonical path, 확장자뿐 아니라 실제 형식·크기·저장위치·경계 이탈(path traversal) 가능성을 필요한 범위에서 검증한다.
5. 암호화·해시·서명 기능이 필요하면 검증된 표준과 유지관리되는 라이브러리를 사용하고 자체 암호 알고리즘을 설계하지 않는다.

## 19. 불변성 우선, 통제된 변경 허용

공유 상태와 외부 입력은 가능한 한 직접 변경하지 않는다. 대용량 배열·GIS·영상 등 복사 비용이 큰 내부 데이터는 소유권이 명확하고 호출자 계약을 깨지 않는 경우에만 in-place 변경을 허용한다.

## 20. 숨은 전역 상태 최소화

전역 변수, singleton, 암묵적 현재상태에 핵심 로직이 불필요하게 의존하지 않도록 한다. 필요한 상태는 입력·명시적 context·의존성 주입으로 전달한다.

## 21. 자원 수명주기 명확화

파일, 소켓, DB 연결, 외부 프로세스, 스레드, 작업 큐, 타이머, 임시파일, 이벤트·signal 연결 등 생성한 자원의 소유자와 종료 책임을 명확히 한다. 성공·실패·취소·예외 모든 경로에서 정리 가능해야 한다.

## 22. 쓰기 작업은 일관성·복구 가능성을 고려

파일·DB·설정 등 영속 상태를 변경할 때 중간 실패가 손상 상태를 남기지 않도록 임시 저장, transaction, atomic replace, rollback, 재실행 안전성 중 필요한 방식을 선택한다.

---

## 22A. 멱등성·중복 실행 안전성

1. 재시도·재실행·중복 callback 가능성이 있는 쓰기 작업은 가능한 한 같은 입력의 반복 실행이 중복 손상·중복 생성으로 이어지지 않도록 설계한다.
2. 멱등하게 만들 수 없는 작업은 idempotency key, unique constraint, 상태전이 검증, 중복실행 guard 등 동등한 보호수단을 둔다.
3. 재시도 가능한 오류와 영구 오류를 구분하고, 비멱등 작업을 실패 원인 확인 없이 자동 재시도하지 않는다.
4. retry는 횟수·시간·backoff 상한을 가지며 원격 시스템 과부하 가능성이 있는 경우 exponential backoff와 jitter를 검토한다.
5. 여러 계층에서 독립적으로 retry하여 시도 횟수가 폭증하지 않도록 재시도 책임 계층을 명확히 한다.

# Part 3. 성능·동시성·환경

## 23. 데이터 규모와 알고리즘 복잡도 사전 고려

대표 데이터 규모를 고려하지 않은 O(N²) 전체스캔, 반복 변환, 반복 정렬, 반복 전체 I/O를 작성하지 않는다. 대량처리가 예상되면 자료구조·인덱스·스트리밍·배치 가능성을 설계 단계에서 검토한다.

## 24. 측정 기반 최적화

캐시, 멀티스레딩, 비동기, SIMD, native extension 등 복잡한 최적화는 실제 병목 또는 명확한 규모 근거가 있을 때 적용한다.

## 25. 성능 개선 순서

기본 순서는 다음과 같다.

```text
불필요한 작업 제거
→ 중복 계산 제거
→ 반복 I/O/파싱 제거
→ 알고리즘·자료구조 개선
→ batch/vectorization/index/streaming
→ 제한된 cache
→ bounded concurrency
→ 필요 시 native acceleration
```

정확성·데이터 무결성·필터 조건을 속도 때문에 희생하지 않는다.

## 26. 동시성은 상한과 종료계약을 가진다

동시작업은 queue·worker·connection·memory 사용량에 상한을 둔다. 무제한 thread/process/task 생성과 무제한 재시도를 금지하며, 취소 시 신규 작업 제출을 중단하고 진행 중 작업의 종료상태를 정리한다.

## 26A. 공유 가변 상태의 thread-safety

1. 여러 thread/process/task가 같은 mutable state를 읽고 쓰는 구조는 경쟁조건(race condition)을 기본 위험으로 본다.
2. 가능한 경우 상태 공유보다 메시지 전달·불변 데이터·작업별 소유권을 우선한다.
3. 동기화가 필요하면 lock 범위와 순서를 작게·일관되게 유지하고, lock을 보유한 채 느린 I/O나 외부 호출을 수행하지 않는다.
4. callback·future·signal이 어떤 실행 context/thread에서 호출되는지 계약을 명확히 한다.
5. thread-safe가 보장되지 않은 객체를 다른 실행 context에서 임의 접근하지 않는다.

## 27. 환경 의존 하드코딩 금지

사용자명, 개인 PC 절대경로, 인증정보, 특정 개발환경 실행파일 경로, 고정 임시폴더 등을 핵심 코드에 박지 않는다. 환경별 값은 설정·환경변수·명령행·런타임 탐색·어댑터 등 적절한 경계에서 주입한다.

## 28. 비밀정보·민감정보 최소 노출

API key, token, cookie, 자격증명, 개인정보를 소스·샘플·로그·오류 메시지에 원문으로 남기지 않는다. 필요한 진단정보는 최소화·마스킹한다.

## 28A. 외부 의존성·도구체인 관리

1. third-party library, runtime, compiler/interpreter, external tool 등 필요한 의존성은 가능한 한 명시적으로 선언한다.
2. 단순 기능을 위해 불필요하게 큰 새 의존성을 추가하지 않는다. 새 dependency 검토 순서는 `stdlib → native/platform → already-installed dependency → small direct implementation → new dependency`를 기본으로 한다.
3. 사용하지 않는 의존성은 제거하고, 유지중단·출처불명·검증하기 어려운 구성요소는 기본 선택으로 사용하지 않는다.
4. 재현 가능한 개발·빌드가 중요한 프로젝트는 lock/constraint/immutable reference 등으로 실제 사용 버전을 재현할 수 있게 한다.
5. 높은 신뢰성이 필요한 배포에서는 패키지 출처·checksum/signature/provenance 등 무결성 검증수단을 제품 위험도에 맞게 사용한다.
6. 전역 개발 PC에 우연히 설치된 도구나 패키지가 없으면 빌드·테스트가 깨지는 숨은 의존성을 만들지 않는다.

## 28B. 시간·난수·로케일의 암묵적 의존 최소화

1. 현재시간, timezone, locale, 환경별 기본 encoding, 랜덤값이 결과 의미에 영향을 주는 경우 이를 계약 또는 주입 가능한 의존성으로 취급한다.
2. 저장·통신 시 시간대·단위·encoding을 모호하게 두지 않는다.
3. 테스트 가능한 코드에서는 현재시간·난수·외부 환경을 필요에 따라 주입하거나 고정할 수 있게 한다.
4. 정렬순서·hash 순서·파일열거 순서처럼 환경에 따라 달라질 수 있는 순서를 공개 결과 계약으로 암묵적으로 사용하지 않는다.

# Part 4. 변경·호환성·검증

## 29. 작은 단위의 변경

한 번의 변경에는 하나의 주된 목적을 둔다. 기능추가, 대규모 리팩토링, UI 변경, 데이터 schema 변경, 성능개선을 필요 이상으로 섞지 않는다.

## 29A. 일관된 스타일·자동 정적검사

1. 해당 언어·프로젝트의 합의된 style guide가 있으면 이를 따른다. 개인 취향을 새 규칙처럼 강제하지 않는다.
2. formatter/linter/compiler warning/type checker/static analyzer가 제공되는 환경에서는 실용적 범위에서 자동화해 일관성을 유지한다.
3. warning·lint·type 오류를 전역 disable로 숨기지 않는다. 예외가 필요하면 가능한 한 좁은 범위에서 이유를 남긴다.
4. 대규모 reformat, import 정렬, rename-only 변경은 기능수정과 분리하여 실제 로직 변경을 검토하기 쉽게 한다.

## 30. 공개 계약·저장형식 호환성 보호

공개 API, 파일형식, DB schema, 설정 key, CLI, 데이터 의미, 사용자가 의존하는 동작을 변경할 때는 영향범위를 확인한다. 호환성이 필요한 경우 migration, bridge, versioning 또는 명시적 폐기 절차를 둔다.

## 31. 테스트 가능한 구조

핵심 로직을 UI, 현재시간, 실DB, 실네트워크, 특정 장치에 직접 결합하지 않는다. 필요한 의존성을 경계 밖으로 분리해 단위시험·fixture·대체 구현이 가능하게 한다.

## 31A. 테스트 품질과 결정성

1. 테스트는 구현 세부보다 사용자·호출자가 관찰하는 동작과 계약을 검증한다.
2. 정상 경로뿐 아니라 변경과 관련된 경계값·실패·취소·부분결과·호환성 경로를 필요한 범위에서 검증한다.
3. 테스트는 동일 조건에서 재현 가능해야 하며 실시간·실네트워크·무작위성·전역상태에 불필요하게 의존하지 않는다.
4. 새 로직이나 버그 수정에는 비용 대비 합리적인 경우 회귀 테스트 또는 동등한 자동 검증을 함께 추가한다.
5. 테스트 코드도 production 코드처럼 단순성·가독성·유지보수성을 지키고 과도한 mocking으로 실제 계약을 가리지 않는다.
6. 테스트가 깨진 코드를 통과시키기 위해 assertion을 약화하거나 테스트를 삭제하는 방식으로 수정하지 않는다.

## 31B. 주석·문서화는 의도와 계약을 설명

1. 코드만 읽어도 알 수 있는 `무엇을 하는지`를 장황하게 반복하기보다, 코드만으로 드러나지 않는 `왜 이렇게 해야 하는지`, 제약, trade-off, 호환 이유를 기록한다.
2. 공개 API·복잡한 알고리즘·비직관적 workaround는 사용법·전제조건·실패 방식·부작용을 필요한 수준에서 문서화한다.
3. 코드 변경으로 사실이 아니게 된 주석·TODO·문서도 함께 수정하거나 제거한다.
4. TODO는 가능하면 해결 조건·이유·추적 가능한 작업 식별자를 남기고 영구적인 변명 주석으로 방치하지 않는다.
5. 설명이 지나치게 길어야 이해되는 코드는 주석을 늘리기 전에 코드 구조 자체를 단순화할 수 있는지 검토한다.

## 31C. 의도적 단순화의 한계와 승격 조건

현재 규모에서는 단순한 구현이 최선이지만 명확한 한계가 있는 경우, 필요한 때에만 **현재 한계와 승격 조건**을 짧게 남길 수 있다.

권장 형식 예:

```text
ponytail: linear scan acceptable below 10k rows; upgrade when p95 > 100 ms
```

또는 프로젝트 표준 주석 형식으로 같은 의미를 기록한다.

1. 막연한 `나중에 개선`, `TODO optimize`만 남기지 않는다.
2. 한계는 구체적이어야 하고, 승격 조건은 가능하면 관찰·측정 가능해야 한다.
3. 보안·데이터 무결성·정확성 결함을 의도적 단순화로 정당화하지 않는다.
4. 단순화 표식 자체가 불필요한 경우 주석을 추가하지 않는다.

## 31D. 최소 실행검증

1. branch, loop, parser, 상태전이, 금액·보안·쓰기 경로 등 비단순 로직 변경에는 가능한 한 **하나 이상의 실행 가능한 검증**을 남긴다.
2. 우선순위는 `기존 관련 test → 기존 test에 focused case 추가 → 작은 test 추가 → 최소 assert/self-check` 순으로 한다.
3. trivial literal 변경·명백한 one-line 치환에 검증 코드를 억지로 추가하지 않는다.
4. 검증 프레임워크가 없는 작은 프로젝트에 단일 검증 때문에 무거운 새 test framework를 도입하지 않는다.
5. 버그 수정은 비용 대비 합리적인 경우 해당 결함이 다시 발생하면 실패하는 regression check를 우선한다.

## 32. 변경범위 내 보이스카우트

수정한 코드와 직접 영향범위 안에서 명백한 중복·죽은 코드·오류 가능성·가독성 문제를 개선할 수 있다. 관련 없는 정상 영역을 ‘정리’ 목적으로 함께 리팩토링하지 않는다.

## 33. 변경영향 분석

공용 함수, 데이터 구조, 공개 API, 저장형식, 상태모델, thread 경계, 자원 소유권을 수정하면 호출부·의존부·인접 workflow 영향을 먼저 확인한다.

## 34. 검증은 변경영향에 비례

코드 변경의 최소 검증은 변경 영역의 syntax/import/static check와 targeted test/regression이다. 전체 회귀, 패키지, OS/장치 실기, stress/soak 등은 제품·릴리즈 시방서가 요구하거나 해당 영역이 변경된 경우 수행한다. 수행하지 않은 항목을 PASS로 추정하지 않는다.

## 34A. 결함 수정은 원인과 재발 방지까지 확인

1. 증상만 숨기는 예외처리·조건문 추가보다 실제 원인을 우선 확인한다. 수정하려는 공통 함수·상태·계약의 주요 caller와 sibling path를 찾아 같은 원인이 반복되는지 점검한다.
2. 동일 원인이 다른 경로에도 존재하면 가능한 범위에서 공통 원인을 한 번 수정한다. 단, 의미가 다른 경로를 단순히 코드가 비슷하다는 이유로 강제 통합하지 않는다.
3. 재발 가능성이 있는 버그는 회귀 테스트·검증 규칙·불변조건 중 적절한 수단으로 다시 검출 가능하게 한다.
4. 보안 결함은 같은 취약 패턴이 다른 입력경계·호출부에 반복되는지 추가 확인한다.

## 34B. 진단 가능성·관측성

1. 실패가 발생했을 때 원인·단계·대상·상태를 추적할 수 있는 최소한의 진단 문맥을 남긴다.
2. 로그·metric·trace는 실제 소비자와 위험도에 비례해 사용하며 모든 값을 무조건 기록하지 않는다.
3. 민감정보·비밀값은 기록하지 않거나 마스킹하고, 로그 인젝션이 가능한 외부 문자열은 안전하게 처리한다.
4. 같은 오류를 여러 계층에서 중복 기록해 noise를 만들지 않도록 기록 책임을 정한다.
5. 진단 기능 자체가 정상 처리의 성능·안정성을 과도하게 해치지 않도록 상한·level·샘플링을 고려한다.

# Part 5. 기본 금지 패턴

다음을 기본 금지한다.

- bare `except` 또는 예외 무시
- 실패를 성공 상태·빈 정상값으로 위장
- 동일 업무규칙·상태판정 복제
- 개인 PC 경로·비밀값 하드코딩
- UI·핵심 로직·저장·네트워크를 한 함수/클래스에 과도하게 혼합
- 종료 경로 없는 Worker/Thread/Process/Task
- 무제한 병렬처리·무제한 retry·무제한 cache
- 중간 실패 시 원본을 손상할 수 있는 직접 덮어쓰기
- 관련 없는 정상기능 동시 수정
- 측정 근거 없는 복잡한 최적화
- 의미 없는 과도한 클래스·파일·추상화 계층 분할
- 실제 두 번째 구현이 없는 interface/factory/strategy를 미래 확장성만으로 추가
- 동작을 그대로 전달할 뿐인 wrapper/service/repository 계층을 의미 없이 추가
- 표준 라이브러리·플랫폼 네이티브 기능·기존 dependency로 해결 가능한 기능을 새 dependency로 재구현
- 한 번만 쓰이는 기능을 범용 utility로 승격하여 public surface를 불필요하게 확대
- 기능별 세부값을 `common/config/constants/utils` 한곳에 누적
- 로컬 결함을 전역 mutable state·공용 stylesheet·root logger·global event 변경으로 해결
- consumer별 변경 이유가 다른데 DRY만을 이유로 강제 공통화
- 실제 소비자가 없는 중복 상태·규칙·출력물 생성
- SQL/shell/HTML/URL/파일경로 등에 외부 입력을 안전한 경계 없이 직접 문자열 결합
- 검증되지 않은 자체 암호화·해시·서명 알고리즘 설계
- 이유 없는 전역 lint/type/static-analysis disable
- 선언되지 않은 숨은 runtime/build dependency 또는 사용하지 않는 third-party dependency 방치
- 중복실행 보호 없이 비멱등 쓰기 작업을 자동 retry
- 현재시간·실네트워크·무작위 전역상태에 불필요하게 의존하는 flaky test
- 장기간 주석 처리된 dead code를 버전관리 대신 소스에 보관

# Part 6. 코드 변경 최소 체크

### 변경 전

- 변경 목적과 직접 영향범위를 정의했는가?
- 이 기능 자체가 현재 요구에 정말 필요한가?
- 같은 기능·helper·pattern이 기존 코드에 이미 있는지 검색했는가?
- 표준 라이브러리·플랫폼 네이티브 기능·기존 dependency로 먼저 해결할 수 없는가?
- 사용자 데이터·공개 계약·저장형식에 영향이 있는가?
- 데이터 규모·외부 입력·권한·동시성 위험을 확인했는가?
- 새 외부 의존성이 정말 필요한지, 출처·버전·재현성이 적절한지 확인했는가?
- 값의 단위·시간대·encoding·null/empty 의미처럼 암묵적 계약이 없는가?
- 기존 authoritative source를 우회하여 같은 규칙을 새로 만들고 있지 않은가?
- 변경 대상의 owner가 local/shared/contract 중 어디인지 식별했는가?
- shared 변경이라면 실제 소비자와 의도된 전파범위를 확인했는가?

### 변경 중

- 책임과 계층 경계가 유지되는가?
- 상태·오류·취소·자원 소유권이 명확한가?
- 외부 입력이 SQL/shell/HTML/path 등 민감한 출력경계에 직접 결합되지 않는가?
- formatter/linter/type/static check 경고를 넓게 숨기지 않았는가?
- 성능 개선 때문에 정확성·안전성을 희생하지 않는가?
- 불필요한 새 파일·class·interface·factory·wrapper·config를 만들고 있지 않은가?
- 같은 결함을 여러 caller에서 반복 patch하지 않고 공통 원인을 수정할 수 없는가?
- 변경 범위 밖 정상기능을 건드리지 않는가?
- local 문제를 해결하기 위해 shared/global 경계를 불필요하게 수정하고 있지 않은가?

### 변경 후

- 핵심 경로가 단순하고 읽기 쉬운가?
- 성공·부분성공·실패·취소 상태를 구분할 수 있는가?
- 자원이 정상 정리되는가?
- 비단순 변경에 최소 하나의 실행 가능한 검증이 있는가?
- 변경 영역 targeted test/regression을 통과했는가?
- 새 로직·버그 수정에 필요한 회귀 테스트와 실패/경계 조건 검증이 있는가?
- 변경으로 주석·문서·공개 계약 설명이 오래된 정보가 되지 않았는가?
- 재시도·재실행 가능한 쓰기는 중복실행 안전성이 있는가?
- 더 넓은 Gate가 필요한 경우 상위 시방서에 따라 수행하거나 PENDING으로 남겼는가?
- 대표 unrelated 영역이 의도치 않게 변하지 않았는지 필요한 격리 회귀를 확인했는가?

- 특정 GUI/QGIS thread-affinity와 UI lifecycle 세부
- 특정 언어의 naming convention, line length, import order

# 부록 B. Ponytail 원칙 통합 요약 — v1.3

v1.3은 Ponytail을 별도 실행모드나 특정 AI 호스트 규칙으로 추가하지 않고, 기존 범용 시방서의 판단 규칙에 흡수했다.

| Ponytail 핵심 | v1.3 반영 위치 | 범용화 방식 |
|---|---|---|
| YAGNI first | 0.3, 3 | 기능 자체의 필요성부터 확인 |
| Reuse before rewrite | 0.3, Part 6 변경 전 | 기존 helper·pattern 검색을 신규 구현보다 우선 |
| Stdlib first | 0.3, 28A | 표준 라이브러리 우선 |
| Native platform first | 0.3, 28A | OS·브라우저·DB·framework 네이티브 기능 우선 |
| Existing dependency before new dependency | 0.3, 28A | 이미 설치된 dependency 우선 |
| Minimum code that works | 0.3, 11D | LOC보다 최소 필요 복잡도·최소 작업면적으로 재정의 |
| Root cause, not symptom | 34A | 주요 caller·sibling path 확인 후 공통 원인 수정 |
| No speculative abstractions | 3, Part 5 | single-implementation interface/factory/wrapper 등을 기본 억제 |
| Fewest files / shortest correct diff | 11D, 29 | 올바른 계층을 전제로 변경면적 최소화 |
| Deletion/reuse over addition | 11D | 삭제·재사용·치환 우선 |
| Deliberate simplification marker | 31C | 한계와 측정 가능한 승격 조건 기록 |
| One runnable check for non-trivial logic | 31D, 34, Part 6 | 기존 테스트 우선, 없으면 최소 self-check |
| Never cut security/validation/data-loss protection | 0.3, Part 2 | 단순화 예외가 아닌 상위 불변 규칙으로 유지 |

### 의도적으로 반영하지 않은 Ponytail 호스트 전용 요소

다음은 범용 코드 시방서의 책임이 아니므로 포함하지 않는다.

- Claude Code/Codex/OpenCode plugin 설치 명령
- lifecycle hook와 매 턴 자동주입 방식
- slash command 및 `lite/full/ultra` 세션 모드
- 응답 문체·설명 길이 제약
- 특정 AI 모델·호스트의 prompt persistence 방식
- 고정 benchmark scorecard

즉 v1.3에서 Ponytail은 **도구나 AI 기능이 아니라 코드 판단 규칙**으로 흡수된다.

## 최종 선언

이 문서는 특정 프레임워크의 코딩 스타일이나 특정 AI의 작업방식을 강제하는 문서가 아니라 **코드를 안전하고 정확하게, 그리고 필요한 만큼만 변경하기 위한 공통 판단 기준**이다. 전용 시방서는 본 원칙을 구체화할 수 있으나 안전성·정확성·공개계약 보호를 약화시키거나, 단순한 LOC 감소를 위해 전체 시스템 복잡도와 변경영향을 키우는 방향으로 해석하지 않는다.
